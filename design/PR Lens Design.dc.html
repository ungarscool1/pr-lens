PR Lens Design proposal v0.1 Awaiting approval · no code yet

A private, local review layer for GitHub pull requests

PR Lens fetches a PR or an arbitrary ref range, runs one read-only Claude pass through your own claude CLI, and overlays ranked attention points on a GitHub-style diff. Everything stays on 127.0.0.1 until you explicitly promote a note to a pending review comment.

Assumptions

Platform. macOS first, Linux second. Windows is out of scope (node-pty and external-terminal launching differ too much).

Single user. One browser tab against one local server. No multi-user locking.

github.com only. GHE is a later config switch (API base URL), not designed for now.

Toolchain. Node 20 LTS+, pnpm workspaces, git ≥ 2.38, gh and claude on PATH.

Hono over Fastify. Its typed RPC client lets the Vite app import route types directly from the server, so the API contract is checked at compile time. WebSockets via @hono/node-ws. Fastify would also work; this is a preference, not a hard reason.

Local git is the diff source. GitHub's files API truncates large patches and the compare API caps at 300 files. A blobless clone gives exact diffs, full file contents, git grep for callers, and the worktrees feature 4 needs anyway.

Storage. SQLite (better-sqlite3) for rows; plain files for large blobs (diff models, raw prompts and outputs).

Model. Whatever claude defaults to, overridable in settings (--model).

01

Architecture

Components

Data flow: opening a PR

Steps 5 and 6 are the only points where Claude usage can occur. A cache hit returns in step 5 with zero CLI calls.

1 · ResolveURL or owner/repo#n → target. Unknown input is rejected before any network call.
2 · MetadataOne GraphQL query: title, body, refs, SHAs, labels, closingIssuesReferences. Issue refs in the body (#123) fetched too, max 3.
3 · FetchBlobless bare clone (first time), then git fetch origin main pull/812/head. Works for forks.
4 · Diff modelgit merge-base, git diff -M --unified=3 → parsed files, line IDs, noise flags, heuristic risk. Written to cache/diffs/.
5 · Cache checkLook up analysis key. Hit → load notes. Miss → token estimate; auto-run only under the threshold (default 60k input tokens).
6 · Review passBuild context, redact secrets, chunk, spawn claude -p per chunk, validate and repair anchors, merge, rank, cap.
7 · PersistAnalysis row, notes, usage; raw prompts and envelopes under runs/<id>/ (0600).
8 · RenderSSE progress per chunk; notes mounted as react-diff-view widgets under their anchor lines.

Diff renderer: react-diff-view

Notes have to be interactive React components (collapse, dismiss, Ask Claude, promote) attached under specific lines. react-diff-view has a widgets prop keyed by change key for exactly this, supports unified and split via viewType, and parses raw git diff output through gitdiff-parser. Syntax highlighting runs through refractor in a web worker. diff2html renders an HTML string, so notes would have to be patched into its DOM after render and re-patched on every update. Its output is good for static reports, not for an editable overlay.

Data model

Cache keys

Three levels. The subject has no SHA and owns things that should survive a force-push: my private notes and seen/dismissed state. The target pins exact SHAs. The analysis key adds everything that changes model output, so editing noise globs or switching models never serves a stale result.

subject   pr:acme/api#812
          cmp:acme/api:v1.4...v1.5
target    pr:acme/api#812@3f2a91c..9bd04e1            merge-base..head (full SHAs stored)
          cmp:acme/api:3f2a91c..77e0b12:two-dot
analysis  sha256(target | prompt_version | model | context_hash)
          context_hash = sha256(noise globs, token budgets, enabled context tiers, redaction rules version)
diff file cache/diffs/sha256(target).json

DiffModel (shared zod type)

type DiffModel = {
  target: string
  mode: 'three-dot' | 'two-dot'
  baseSha: string; headSha: string; mergeBaseSha?: string
  files: DiffFile[]                     // sorted by path → deterministic F-numbers
}
type DiffFile = {
  fid: string                           // 'F1'
  path: string; oldPath?: string
  status: 'added' | 'modified' | 'deleted' | 'renamed' | 'binary'
  additions: number; deletions: number
  noise?: { reason: 'lockfile' | 'generated' | 'snapshot' | 'vendored' | 'glob'; rule: string }
  heuristicRisk: 'high' | 'medium' | 'low'   // path rules + size, shown before AI runs
  hunks: { header: string; lines: DiffLine[] }[]
}
type DiffLine = {
  id: string                            // 'F1-007'; ordinal within file, zero-padded
  kind: 'add' | 'del' | 'ctx'
  old?: number; new?: number            // real line numbers per side
  text: string
  changeKey: string                     // react-diff-view key, e.g. 'I42'
}

When a PR's head moves, a new target is created. My notes from the previous target are copied forward and re-anchored by fingerprint (exact match, then best fuzzy match within the same file). Notes that cannot be placed are kept with outdated = 1, the same idea as GitHub's outdated comments.

03

Review pass: prompts, schema, anchoring

Line-ID anchoring

Files are sorted by path and numbered F1…Fn across the whole diff, including noise files, so IDs never collide between chunks.

Every diff line gets F<n>-<ordinal>, counted across hunks, zero-padded to at least 3 digits. Context, added and removed lines all get IDs.

The prompt shows ID, marker and text. No line numbers appear, so the model has nothing else to cite.

Each note also carries a quote: an exact fragment of its start line. Validation uses it to repair bad IDs.

Context snippets (full files, callers, tests) are labelled C1, T1 and can be cited in refs, but are never valid anchors.

After validation, IDs are resolved to path, side and real line numbers. Those are what the UI and the GitHub API use.

Invocation

Context assembly

Filled in tier order until the chunk budget (default 90k input tokens, estimated as chars ÷ 3.6) is reached. Lower tiers are dropped first; the manifest records what was left out.

TierContentSource
T0PR header, description, linked issues (bodies truncated to 2k chars each)GraphQL snapshot in meta_json
T1Manifest of all files: ID, path, status, ±counts, noise reason, in-this-chunk flagDiffModel
T2Diff with line IDs for this chunk's non-noise filesDiffModel
T3Full head content of changed files under 600 linesgit show head:path
T4Related tests: same basename with .test/.spec/_test, or under __tests__git ls-tree + path rules
T5Callers of exported symbols whose signature or body changed: top 8 hits, ±6 lines eachgit grep -n -w <symbol> head

System prompt — review.v1/system.md

You are PR Lens, a private review assistant for an experienced engineer who
reviews many pull requests. Your output is never shown to the PR author.

Find the few things a careful senior reviewer would stop and look at:
behavior changes, security, concurrency, API breaks, data migrations,
error handling, missing tests, performance and correctness bugs.
Skip style, naming, formatting and anything a linter or type checker catches.

Be specific. Name the function, the caller, the input that breaks it. When a
claim relies on a context snippet, list its ID (C1, T1, F2) in refs. Never
describe code you have not been shown. If you are unsure, lower confidence
rather than hedging in prose.

Return only the JSON object defined by the provided schema.

Task
- Return at most 8 notes, ordered by how much they matter. Fewer is better
  than padding. An empty notes array is a valid answer.
- anchor.start and anchor.end are line IDs from <diff> (e.g. F1-005), in the
  same file, end at or after start. Use the smallest span that shows the issue,
  usually 1–6 lines. Never use line numbers.
- Prefer added lines. Anchor to removed lines only when the removal is the issue.
- quote is an exact fragment (at least 8 characters) copied from the start line.
- severity: high = likely bug, security hole or break for callers;
  medium = plausible problem worth asking about; low = worth a glance.
- question, when present, is one sentence I could paste to the author.
- files: a risk level and a short reason for every in-chunk file.
- reading_order: in-chunk file IDs in the order a reviewer should read them,
  definitions and contracts before their users, tests last.
- summary: what this PR does, in at most 3 sentences.

The ID patterns are deliberately loose (F2-03 passes) so the CLI does not reject a whole response over padding; strict normalization happens in validate.ts. The same schema exists as a zod type in packages/shared, and the envelope's structured_output is parsed with it again.

Validation and repair

#CheckOn failure
1Envelope is_error false; structured_output parses with zodOne retry with the same prompt; then mark chunk failed (analysis becomes partial)
2Normalize IDs: trim, uppercase F, zero-pad ordinalMark repaired
3start and end exist in the DiffModelSearch the anchor file (then all in-chunk files) for quote; unique match becomes start, end = start
4start and end in the same file; anchor.file agreesTrust the line IDs over anchor.file; if they span files, collapse to start
5end at or after start; span ≤ 20 linesSwap reversed; truncate long spans to 20 lines from start
6Quote appears on the start line (whitespace-insensitive)If quote matches elsewhere in the span, move start there; otherwise keep but lower confidence by 0.2
7Nothing above locates a line, but the file is knownKeep as a file-level note
8File unknown and quote not foundDrop; listed in the run's "dropped" drawer with the reason

Ranking and cap

score = severity (high 3, medium 2, low 1) × confidence × category weight. Weights: security, api_break, data_migration 1.2; missing_tests 0.8; others 1.0. Low-severity notes under 0.4 confidence are dropped. The top 8 are kept (setting, max 10). A high note is never cut in favour of a lower one.

Large PRs: chunking and merge

Single pass if the assembled context fits one budget. Most PRs never reach the merge step.

Grouping. Source files are kept with their tests, then grouped by top-level directory, then bin-packed largest first. A file larger than the budget is split by hunks.

Per chunk. Every chunk gets the full PR header and manifest, its own diff and context, and is asked for at most 6 notes. Chunks run two at a time.

Merge pass. Input is only the validated candidates (key c2.n1, resolved path:line, the quoted lines) plus per-chunk summaries. No diff. It cannot invent anchors: each final note points to candidate keys and inherits the first one's anchor.

Guard. More than 8 chunks requires confirmation and offers "review selection": pick files or directories in the tree and review only those.

05

Risks and mitigations

RiskMitigation
Anchoring errorsLine IDs instead of numbers; quote-based repair; ID normalization; cross-file and reversed-span fixes; file-level fallback; dropped notes visible, never silent. Fixture suite of malformed outputs in test/fixtures.
Huge PRsNoise filtering before anything else (lockfiles, snapshots, vendor/, dist/, *.min.js, *.pb.go, plus linguist-generated from .gitattributes via git check-attr). Budgeted chunks, hunk splitting, 8-chunk guard, review-selection. UI: files render lazily on scroll, diffs over 400 lines start collapsed, tokenization in a worker.
GitHub rate limitsDiffs and file contents come from git, not the API. One GraphQL query per PR load. ETag conditional requests (304s are free). Refs cached 5 min. Remaining quota shown in the status bar; on 403/429 back off until the reset header.
Credit usageCache hits never call the CLI. Estimate shown before every run; auto-run only under the threshold. Re-runs are manual and show the estimate. Actual tokens and the CLI's cost figure stored per run and shown on the analysis. Cancel kills the process group. Static system prompt and PR header come first so repeat chunks can hit prompt caching.
Secrets in diffsScanner (gitleaks-style rules plus entropy check on added lines) runs before prompt assembly; hits are replaced with typed placeholders («REDACTED:aws-access-key») and listed in a banner. .env*, *.pem, *.key, id_rsa* are excluded entirely. Run files are 0600 with 14-day retention, and prompt storage can be turned off.
Billing switch or token exposureSubprocess env is an allowlist built from scratch, never a copy of process.env minus a few keys. Startup check runs claude auth status and refuses to start review runs if it reports API-key auth. The OAuth token is passed through untouched and never logged, stored or sent anywhere by PR Lens. The GitHub token is never in the Claude env and never in a git remote URL (git auth goes through a GIT_ASKPASS helper).
Prompt injection from PR contentThe automatic pass has no tools and an empty cwd, so injected instructions have nothing to act on. Untrusted content is delimited and labelled. Output is schema-constrained and rendered as sanitized markdown with no raw HTML. Worst case is a misleading note.
Malicious repo config in worktreesA PR can add .claude/settings.json hooks, .mcp.json or a hostile CLAUDE.md. Interactive sessions load user settings only, use strict empty MCP config and start in plan mode. PRs touching those paths get a warning on the Ask Claude button. PR Lens never runs repo scripts or installs dependencies.
Local server as an attack surfaceThe PTY socket is effectively a shell. Bind 127.0.0.1 only. A random launch token in the opened URL is exchanged for an HttpOnly, SameSite=Strict cookie. Host header allowlist (blocks DNS rebinding), Origin checks, no CORS, strict CSP.
Accidental postingWrite token is a separate env var, loaded only when write mode is on. The read client rejects non-GET requests and GraphQL mutations; only promote/ imports the write client. Preview, then single-use confirm token. Pending reviews only; the code path never sets an event. Every promotion is recorded.
Stale results after a pushKeys include merge-base and head SHAs. A "head moved" banner offers refresh. Private notes are re-anchored by fingerprint or marked outdated. Promote is blocked for notes whose target is not the current head.
CLI flag driftFlags verified in Phase 0 and pinned to a minimum claude version checked at startup. Recorded envelopes in tests catch format changes.
